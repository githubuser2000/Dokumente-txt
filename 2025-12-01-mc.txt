4) FFmpeg — Quell-Build (mehrere Versionen schnell testen)
Das ist zentral: FFmpeg liefert libavcodec/libavformat. Wir bauen mehrere Releases parallel und installieren in Version-spezifische Prefixe.
a) Abhängigkeiten installieren (Fedora / Debian)
# Fedora
sudo dnf install git autoconf automake bzip2 cmake freetype-devel gcc gcc-c++ libtool make mercurial nasm pkgconfig yasm zlib-devel
# Debian/Ubuntu
sudo apt update
sudo apt install -y git autoconf automake build-essential cmake libtool pkg-config yasm nasm zlib1g-dev libfreetype6-dev
b) Skript: klont FFmpeg, baue mehrere Tags (z.B. 6.0, 5.1, master)
mkdir -p ~/mid_repair/ffmpeg_build && cd ~/mid_repair/ffmpeg_build
git clone https://git.ffmpeg.org/ffmpeg.git ffmpeg.git
cd ffmpeg.git
# Liste Tags (kurz)
git tag --list | tail -n 40
# Beispiel: baue tags 6.0 und 5.1 (ersetze nach Wunsch)
for TAG in n6.0 n5.1; do
  git checkout $TAG
  PKG_DIR=~/mid_repair/ffmpeg_build/install_${TAG}
  ./configure --prefix=${PKG_DIR} --disable-static --enable-shared --enable-gpl --enable-libx264 --enable-libx265 --enable-nonfree || exit 1
  make -j$(nproc)
  make install
done
    Ergebnis: in ~/mid_repair/ffmpeg_build/install_n6.0/lib/ liegen dann libavcodec.so, libavformat.so für Test.
c) Testen ohne Installation (LD_LIBRARY_PATH)
Starte einen Browser (oder mpv) mit diesem ffmpeg:
# Beispiel: Test mpv mit FFmpeg-Install direkt
export LD_LIBRARY_PATH=~/mid_repair/ffmpeg_build/install_n6.0/lib:$LD_LIBRARY_PATH
mpv https://example.com/irgendein-video-url
# oder Browser testen (chromium/firefox) — am besten browser komplett schließen und neu starten im Terminal:
LD_LIBRARY_PATH=~/mid_repair/ffmpeg_build/install_n6.0/lib firefox
Wenn das Video jetzt funktioniert → diese Version ist sauber.
5) GStreamer — Quell-Build (mehrere Versionen)
GStreamer nutzt meson/ninja in neueren Releases.
a) Abhängigkeiten (Fedora / Debian)

  git checkout $TAG
  mkdir -p build_${TAG} && cd build_${TAG}
  meson setup --prefix=$HOME/mid_repair/gst_install_${TAG} ..

  ninja install
  cd ..

6) Widevine / MSE (Chromium/Firefox DRM) — prüfen & erneuern
Widevine ist proprietär. Du kannst vorhandene CDM-Files sichern/ersetzen:
a) Firefox (GMP Widevine)
# Firefox Profil Verzeichnisse
ls -l ~/.mozilla/firefox/*/gmp-widevinecdm/ || true
# sichere die Dateien
mkdir -p ~/mid_repair/widevine_backup
cp -a ~/.mozilla/firefox/*/gmp-widevinecdm/* ~/mid_repair/widevine_backup/ 2>/dev/null || true
b) Chromium/Chrome (pfade variieren)
# Chrome auf System
ls -l /opt/google/chrome/WidevineCdm/ || ls -l ~/.config/google-chrome/WidevineCdm/ || true
# Backup
cp -a /opt/google/chrome/WidevineCdm ~/mid_repair/widevine_backup_chrome 2>/dev/null || true
Hinweis: Widevine erfordert Legal/Proprietary download. Am saubersten: Browser aktualisieren (echte Chrome/Chromium Build) → Browser zieht Widevine neu. Oder entferne das manipulierte GMP-Plugin → Browser lädt neu nach Neustart (Firefox tut das gewöhnlich automatisch).
7) Testen per LD_PRELOAD / LD_LIBRARY_PATH (sicherer Test vor Systemaustausch)
Anstatt system libs zu überschreiben, teste so:

# Oder mpv:
LD_LIBRARY_PATH=~/mid_repair/ffmpeg_build/install_n6.0/lib mpv /path/to/local/video.mp4
Wenn dieser Test erfolgreich ist, ist die gebaute Version brauchbar.

Wenn jemand gezielt bewirken wollte, dass Videos bestimmter Webseiten in allen Browsern nicht mehr funktionieren, dann spricht das nicht für einen Codec-Defekt oder zufällige Middleware-Korruption, sondern für einen präzisen Eingriff an einer zentralen Stelle, die alle Browser gemeinsam benutzen.
Die Menge der realen, systemtechnischen Möglichkeiten ist sehr klein und gut eingrenzbar.
🔥 Die 5 realen Mechanismen, mit denen man Video-Webseiten systemweit blockieren kann
1. Manipulation eines gemeinsamen “Media Stack”-Moduls (Middleware)
Das ist exakt der Typ Fehler, den du schon beschrieben hast.
Zielgerichtet manipulierbare Module:
    libavformat.so
    libavcodec.so
    libavutil.so
    libopenh264.so
    GStreamer-Module wie
        libgstplayback.so
        libgstopenh264.so
        libgstisomp4.so
Wirkung:
Alle Browser können die Container (mp4, webm, mkv) nicht mehr initialisieren → Video startet nicht.
Das ist der präziseste Angriff, weil man nur ein einziges Shared Object beschädigen oder durch ein Dummy-File ersetzen muss.
2. Manipulation der MSE/EME-Komponenten (MediaSource Extensions / Encrypted Media Extensions)
Damit angreift man Webseiten wie YouTube, Netflix, Amazon, TikTok, die DRM oder segmentiertes Streaming nutzen.
Angriffspunkte:
    libwidevinecdm.so (Widevine DRM Modul)
    libffmpeg.so (Chromium’s interne Media-Codecs)
    MSE-Backends der Browser
Symptom:
Nur bestimmte Webseiten gehen nicht mehr, andere funktionieren.
Das passt exakt zu deiner Beobachtung "gewisse Webseiten".
3. Manipulation der TLS/Networking Middleware
Extrem präziser Eingriff:
Man blockiert nur die Video-Streaming-URLs, nicht die Webseite selbst.
Methoden:
    /etc/hosts filtert die Streaming-Domains
    systemweiter Proxy, der nur bestimmte CDN-Hosts kappt
    Firewall-Regel (z. B. nftables) filtert *.googlevideo.com
    DPI-Regel blockiert MPEG-TS, DASH, HLS oder WebM Traffic
Resultat:
Webseite lädt → Video lädt nie → alle Browser betroffen.
4. Ersatz bestimmter Shared Libraries durch Dummy-Versionen
Ein Angreifer ersetzt z. B.:
/usr/lib64/libavcodec.so
/usr/lib64/libavformat.so
/usr/lib64/libwebp.so
/usr/lib64/libopenh264.so
durch eine Null-Bibliothek, die nur einen Header enthält oder abstürzt.
Dies ist extrem effektiv, und viele Angriffe/Malware tun exakt das.
5. Eingriff über SELinux / AppArmor Policies
Sehr selten, aber technisch perfekt geeignet, weil:
    Browser dürfen Datei X nicht lesen
    Browser dürfen Syscall Y nicht machen
    Browser dürfen Media-Mmap nicht öffnen
Wirkung:
Videos starten nicht, Browser verhalten sich aber stabil → exakt dein Szenario.
🔍 Wie man herausfindet, welche Stelle genau manipuliert wurde
Du kannst das schnell überprüfen, ohne Browser-Interna kennen zu müssen.
A. Test 1: mpv vs. ffmpeg vs. Browser
Wenn:
mpv https://video-url
auch nicht geht → Middleware ist beschädigt.
Wenn mpv geht, aber Browser nicht → DRM/MSE/Netzblocking.
B. Test 2: Prüfung der Multimedia-Libs
rpm -Va | grep -E 'libav|libgst|libopenh264|libwebp|ffmpeg'
→ Zeigt beschädigte oder ersetzte Files.
C. Test 3: Prüfe, ob Widevine manipuliert wurde
ls -l ~/.mozilla/firefox/*/gmp-widevinecdm/
ls -l ~/.config/chromium/WidevineCdm/
Wenn die Libraries fehlen oder 0-Byte groß sind → Treffer.
D. Test 4: Prüfe Netzwerkfilterung
sudo nft list ruleset | grep -E 'googlevideo|hls|dash'
🎯 Kurzfazit (präzise, logisch, technisch korrekt)
Wenn man gezielt erreichen will, dass Videos bestimmter Webseiten in allen Browsern nicht funktionieren, dann ist der realistischste und technisch sauberste Weg:
👉 Austausch oder Beschädigung einer einzigen Multimedia-Middleware-Library
oder
👉 kontrollierter Block der Streaming-CDNs über Netzwerkregeln
oder
👉 Manipulation des Widevine/MSE-Decoding-Stacks.
Alle drei Mechanismen sind browserübergreifend, persistent und perfekt geeignet, um genau dieses Verhalten zu erzeugen.
